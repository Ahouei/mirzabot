01 Executive summary

The rewrite is a well-structured, genuinely more maintainable skeleton that is not yet feature-complete — and, critically, is broken on the one path the whole product exists for: taking money and delivering a config. Architecturally it is a real step up from the PHP monolith: a plugin registry for panels, payments and jobs; an ORM with real foreign keys and indexes; JSONB settings; Fernet-encrypted panel passwords; idempotent payment claiming; and proper Telegram Mini-App signature validation. As a foundation to build on, it succeeds.

Measured against the actual instruction — full feature parity with main — it is roughly half-done, and the missing half includes the revenue path. Three independent defects each break online payments on their own:

#1PaymentService.settle_wallet_topup(…) is called in four places but defined nowhere. Every wallet top-up settlement — Zarinpal, IranPay, Plisio, NowPayments, card-to-card, Telegram Stars — raises AttributeError at runtime.
#2Paying for a product through any online gateway never provisions it. The bot checkout creates the order with no invoice_id, so settlement treats the purchase as a wallet top-up (which then hits #1).
#3The customer is never notified when a gateway payment settles (_notify_user(None, …)) and the admin payment report is a no-op placeholder.

The single biggest risk is therefore not "some features are missing." It is that the money path looks finished — there are gateway modules, a passing test suite, and a self-authored PARITY.md claiming ✅ almost everywhere — yet it does not work end-to-end, and the tests are green because they never exercise the broken branch. Anyone trusting the self-reported matrix would ship a bot that accepts payment and hands out nothing.

Beyond payments, the admin surface is a fraction of the original (~25 mostly create-and-list commands versus ~177 branches in admin.php; no multi-admin support, no in-bot text customization, no per-panel pricing or inbound editing). Several scheduled jobs are stubs or point at the wrong destination — expiry reminders go to an admin channel instead of the customer, the lottery job is absent, and the gift job is literally return None. A number of admin-configurable settings are written but never read (lucky-wheel prizes, gift-code percentages).

02 How this pass was conducted

  • Both branches read directly from git worktrees; no code executed, no dependencies installed, no PostgreSQL or panels contacted.
  • Breadth-first, risk-weighted: every functional area inventoried and mapped; deep line-level scrutiny concentrated on the money path, scheduled jobs, auth, and the data model.
  • The rewrite's own PARITY.md was treated as a claim to verify, not evidence — several of its ✅ entries are contradicted by the code and are called out inline.
  • Where a conclusion is inferred rather than proven by reading, it is labelled as such. The honest depth boundary is stated in §10.

04 Additions in the rewrite ➕

Genuinely useful and mostly aligned with the "improve where reasonable / design for extension" instruction. Crucially, these are labelled in PARITY.md rather than silently mixed into parity work — that instruction was followed. The problem is the false ✅ parity claims sitting beside them.

  • Plugin registry for panels, payments and jobs (@register_plugin) with runtime enable/disable — the main extensibility win.
  • Append-only balance ledger — auditable wallet.
  • Idempotent payment claiming (claim_paid) — correct concurrency guard (undermined in practice by the settle bug).
  • Webhook secret validation — closes a real main gap (fails open if unset).
  • Fernet encryption of panel passwords at rest (weak-default-key caveat).
  • JSONB settings, real FKs and indexes on the invoice/payment hot paths.
  • Proper Telegram initData HMAC validation for the Mini-App — stronger than main.
  • Batched / rate-capped broadcast and payment polling.

05 Architecture & extensibility

This is the rewrite's strongest dimension, and the instruction to "design for future add-ons" was taken seriously rather than producing a literal transliteration. Concretely:

  • Clean module boundaries: handlers/ (bot), panels/ (provisioning adapters), payments/ (gateways), jobs/ (scheduler), api/ (HTTP), models/, i18n/. This is a real separation the PHP monolith (a 10.9k-line admin.php, a 6.7k-line index.php) never had.
  • A genuine plugin system: registry/ plus a contracts.py defining PanelAdapter, PanelResult and Job interfaces. Adding a panel or gateway is a new class with a decorator — the correct extension seam, and the clearest evidence this is designed to grow.
  • Config-driven where it counts: a settings KV store and per-panel columns replace scattered PHP constants; the scheduler is toggleable like the legacy status_cron.

The extensibility is undercut in three places where the design reverts to hardcoding: process-local dictionaries for purchase, top-up, broadcast and web-session state (breaks multi-worker and restarts); single-admin gating that ignores the Admin/rule tables; and hardcoded values that shadow admin config (wheel prizes, trial limits). The bones are extensible; several muscles are still nailed in place.

08 Recommended next steps

Must fix before replacing main   — the "make the core actually work" tranche (1–7); land together with an end-to-end test.

  1. Define PaymentService.settle_wallet_topup(order, cashback_pct=0) and cover it with a settlement test — unblocks all gateway top-ups + Stars.
  2. Set invoice_id on gateway product orders in buy.py::pay_gateway so purchases provision instead of top up.
  3. Wire a real bot into payhooks settlement — implement buyer DM and the admin report.
  4. Fix wallet-purchase ordering: charge → provision in one transaction; re-verify balance atomically.
  5. Fix change-location and manual-sell to carry real volume / expiry.
  6. Point expiry & volume reminders at the customer; commit disableconfig.
  7. Move ephemeral state to the DB / Redis (aiogram FSM) — removes the race and multi-worker breakage.

Reach real parity   — the second tranche (8–14).

  1. Restore money-adjacent admin parity: multi-admin gating, per-panel pricing/inbound/test config, product edit/delete, discount %/limits, card-number management, in-bot text customization.
  2. Rewrite the discount engine (percent + fixed + per-product + usage-limit + expiry) and increment used_count.
  3. Real migrations: replace the create_all shim with explicit DDL, and ship the compatibility view the settings redesign depends on.
  4. Port the lottery job; implement gift drops; connect /wheelprizes to the wheel.
  5. Referral commission & cashback; phone-verification enforcement; the on-hold creation path.
  6. Harden config: require non-default secrets at boot; separate the encryption key from the session secret; add Secure cookies and consistent escaping.
  7. Add end-to-end tests for the full purchase journey per gateway before re-claiming parity.

09 What could not be verified statically

Deferred to the second (live-run) pass:

  • Panel adapters against real panels. Only marzban.py was deep-read (looks faithful). Marzneshin, Alireza/x-ui, S-UI, Hiddify, WGDashboard (keygen), MikroTik (REST v7), IBSng, Pasarguard, Rebecca and mirza_agent need live create/modify/remove/revoke round-trips.
  • The end-to-end purchase → payment → provision → notify flow per gateway — confirm the §6 crashes and the top-up mis-route on a running instance.
  • Alembic upgrade/downgrade against real PostgreSQL (JSONB, FKs, the missing compat view, the absent protocol table).
  • Gateway callback signatures against live sandboxes (Zarinpal v4, Aqayepardakht code-70, Plisio/NowPayments webhooks, IranPay poll, CubePay HMAC).
  • The Mini-App inside Telegram (real initData, token exchange, purchase actions), scheduled jobs on the real scheduler, white-label child-bot dispatch, and the installer on a clean host.
